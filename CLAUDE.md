# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

**RepoLens** is a public Next.js app that turns any GitHub repository into a fast, indexable insight page, with a signed-in watchlist and a streaming "ask this repo" AI assistant. It is a portfolio project meant to show lead-level frontend work. The full plan is in `PLAN.md`. Read it before starting a new week's work.

**Main rule:** every change should produce frontend evidence: rendering strategy, performance, accessibility, design system, type safety or tests. Keep backend work minimal. Don't add services, queues or abstractions that a frontend reviewer wouldn't look at.

## Next.js version

This is **Next.js 16.4 with Cache Components and Partial Prefetching enabled** (`apps/web/next.config.ts`). Its APIs differ from older Next.js. Before writing routing, caching or data-fetching code, read the bundled docs in `node_modules/next/dist/docs/` (see `apps/web/AGENTS.md`). `next dev` rewrites that file, so commit it rather than deleting it. The root `AGENTS.md` is the same idea for Turborepo: read the bundled `turbo` docs before changing `turbo.json`.

## Repository layout

A pnpm + Turborepo monorepo:

```
apps/web/          Next.js App Router app
packages/ui/       Design system: tokens, Radix-based components, Storybook
docs/adr/          Architecture Decision Records, one page each (NNNN-title.md)
docker-compose.yml Local Postgres
```

Don't add a new package without an ADR. Shared UI goes in `packages/ui`. App-specific components stay in `apps/web`.

## Commands

Run these from the repo root. Turborepo fans them out to the workspaces.

```bash
pnpm install
docker compose up -d     # local Postgres
pnpm dev                 # Next.js dev server (runs codegen first)
pnpm build               # needs GITHUB_TOKEN: the home page prerenders live GitHub data
pnpm lint
pnpm typecheck           # next typegen + tsc --noEmit across workspaces
pnpm test                # Vitest + React Testing Library, all workspaces
pnpm codegen             # GraphQL Code Generator → apps/web/src/gql (gitignored)
pnpm format              # Prettier (format:check runs in CI)
```

Planned, not yet added: `pnpm test:e2e` (Playwright, week 6) and `pnpm storybook` (`packages/ui`, week 2).

Run a single test file with `pnpm --filter web exec vitest run src/lib/github/client.test.ts`.

To scope a command to one workspace, use `pnpm --filter web <script>` or `pnpm --filter @repolens/ui <script>`.

## Stack

Next.js (latest stable, App Router) · strict TypeScript · Tailwind CSS · Radix primitives · GraphQL Code Generator (typed documents) · TanStack Query · Auth.js (GitHub OAuth) · Neon Postgres + Kysely · Vercel AI SDK · Vitest + React Testing Library · Playwright · Storybook · GitHub Actions · Vercel.

Don't add a dependency that overlaps these, such as Apollo, Redux, an ORM besides Kysely, or another component library, without an ADR.

## Rendering strategy

Each route has a deliberate rendering mode. Don't change one without updating ADR 3.

| Route | Rendering |
| --- | --- |
| `/` | SSG |
| `/[owner]/[repo]` | ISR via Cache Components. Popular repos are pre-built with `generateStaticParams`, and the rest get the App Shell and are cached after their first visit. Await `params` *inside* `<Suspense>`. Slow panels (contributors, activity) stream behind their own boundaries |
| `/search` | Dynamic SSR from search params. All filter state lives in the URL |
| `/watchlist` | Server-rendered shell, with client data via TanStack Query |
| `/api/chat` | Route handler with a streaming response |

Conventions:

- **Server Components by default.** Add `"use client"` only for interactive islands, and push it as far down the tree as possible. Every client boundary adds to the first-load JS budget.
- Every route segment that fetches data gets `loading.tsx`, `error.tsx` and `not-found.tsx` where they apply.
- Each Suspense fallback uses `Skeleton` from `packages/ui` and matches the final layout's dimensions so it causes no CLS.

## Data: GitHub GraphQL

- **Only call the GitHub API on the server.** The token must never reach the client bundle. Don't prefix it with `NEXT_PUBLIC_`.
- Use plain typed `fetch` with documents generated by GraphQL Code Generator. Don't use Apollo or urql (see ADR 2).
- Write queries with `graphql()` from `@/gql` next to the function that uses them, then run `pnpm codegen`. Never hand-write response types. Derive component prop types from the generated query types (see `RepoCard`).
- The schema comes from `@octokit/graphql-schema`, so codegen works offline. Documents are emitted as `TypedDocumentString` (`documentMode: "string"`), and `src/gql/` is generated and gitignored.
- Send every request through `githubQuery()` in `src/lib/github/client.ts`. It is `server-only` and maps failures to `GitHubError` with a `kind` (`rate-limited`, `unauthorized`, `not-found`, `unknown`) that the UI can branch on.
- **Caching uses the Cache Components model, not `fetch` options.** Each data function starts with `"use cache"` and calls `cacheLife(...)` and `cacheTag("repo:owner/name")`, as in `src/lib/github/repo-summary.ts`. Mutations invalidate by tag.
- The API is rate-limited. Request only the fields a page renders, and treat rate-limit errors as a UI state, not a crash.

## Auth, watchlist and mutations

- Auth.js uses the GitHub provider. Access the session on the server.
- Mutations (add/remove watchlist) are Server Actions that revalidate the affected cache. On the client, TanStack Query handles optimistic updates with rollback on error (see ADR 4).
- DB access uses Kysely only, with typed schema. Migrations live in the repo.

## AI assistant

- Vercel AI SDK. `/api/chat` builds context **server-side** from the README and recent issues. The client never sends raw repo content.
- Chat UI uses `useChat` and must handle stop, retry, loading, error and rate-limit-hit states, all keyboard accessible.
- Apply per-user rate limiting. Watch cost when you change context selection, and record it in ADR 6.
- Tests mock the model. No live model calls in CI.

## Testing

- Use Vitest with `globals: true` and jsdom. Test files sit next to their source as `*.test.ts(x)`.
- Vitest can't render **async Server Components**. Keep them thin: put the logic in pure functions and sync components, unit-test those, and cover the async page with Playwright.
- Mock GitHub by stubbing `fetch` (`vi.stubGlobal`) and set env with `vi.stubEnv` (see `client.test.ts`). `server-only` is aliased to an empty module in `vitest.config.mts`.

## Design system (`packages/ui`)

- Tokens (color, spacing, type) are CSS variables, and Tailwind consumes them. Don't hard-code colors or spacing in components.
- Build components on Radix primitives. Each component ships with:
  1. a Storybook story with a docs page (and no a11y addon violations)
  2. a React Testing Library test
- Components are app-agnostic, so `packages/ui` must never import from `apps/web`.

## Quality bars (enforced in CI)

The project is "done" when CI enforces these on every PR. Treat them as hard constraints on every change:

- **Core Web Vitals (repo page, mobile):** LCP < 2.5 s, INP < 200 ms, CLS < 0.1
- **Lighthouse (mobile):** ≥ 95 in Performance, Accessibility, Best Practices and SEO
- **First-load JS (repo page):** stays within the budget set in week 3. Raising it requires an ADR.
- **Accessibility:** zero axe violations, and a full keyboard path through search, watchlist and chat
- **Tests:** every `ui` component and every data hook has a test. E2E covers search, sign-in, add to watchlist and asking the assistant, with GitHub and AI mocked.
- **SEO:** `generateMetadata`, canonical URLs, valid JSON-LD, a sitemap covering all pre-rendered repos, and a unit test on the metadata builder
- **Types:** strict TS and no `any`, including no `as any` or `@ts-ignore`. Fix the type instead.

Before calling a task finished, run `pnpm lint && pnpm typecheck && pnpm test` and report the results honestly.

## Working conventions

- **Tests and ADRs land in the same week (ideally the same PR) as the feature.** Never defer them.
- ADRs live in `docs/adr/` and are one page each: Context → Decision → Consequences → Alternatives considered. The six planned ADRs:
  1. App Router over a Vite SPA
  2. Plain typed `fetch` for GraphQL instead of Apollo
  3. Rendering strategy per route
  4. Server Actions vs route handlers + TanStack Query
  5. Design-system package boundaries and token structure
  6. AI assistant: context selection, cost, rate limiting, failure UX
- When a change involves a real trade-off, such as caching behavior, a client boundary or a new dependency, say so and suggest whether it deserves an ADR or an update to an existing one. The ADRs are what reviewers read.
- Ship must-have features before any stretch item: AI summary, repo compare, dark mode and reduced motion, visual regression.
- Secrets stay in `.env.local`, which is never committed. Keep `.env.example` up to date.
